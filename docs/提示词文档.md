## 一、需求梳理阶段

### 1.1 项目启动（从一张实物图开始）

```
这是一种名字叫《军旗》的纸牌游戏，我想把它做成小程序让用户可以通过小程序来玩，
卡片图片要保持一致，游戏规则要跟纸牌《军旗》游戏规则一致，先完善需求文档
```

**要点**：先出需求文档、不动代码；卡面直接用原图、不重绘；规则以实体纸牌为准。
**效果**：产出需求文档 v0.1（牌组考证 + 规则 + 技术方案 + 待确认问题清单）。

### 1.2 玩法修订（核心规则调整）

```
出牌方式改为翻牌+格子移动，5列 × 5行 的正方形网格（共25个格子）
这正好对应图里25张牌的数量，所有纸牌随机反面覆盖在格子上，
用户可以翻牌或者选取自己一方已经翻开的卡片移动一个格子，
然后轮到对方，对方也是可以翻牌或者选取自己一方已经翻开的卡片移动一个格子
```

**要点**：用户用自然语言描述完整玩法，AI 负责规则化、边界补全（定色、和棋、死局）。
**经验**：玩法级改动要连带修订交互、AI 策略、数据结构，一次说清避免多轮。

### 1.3 胜负条件修订

```
只能把对方所有消灭才能夺旗
```

**经验**：短提示词 + 已有文档上下文即可精准落档；AI 需连带处理边界（对方全灭后找旗、双方全灭平局）。

### 1.4 逐项拍板（批量确认待定问题）

```
1.定色规则不改 2.军官撞地雷用你小时候玩的是"同归于尽"
4.默认每次只可向上下左右相邻一格移动，不支持斜走，不支持连续多格
5 是的，先挖雷后扛旗 6.仅微信小程序 7 目前没有更高清的图了
8 可接收 9 以个人
```

**经验**：AI 先在文档里列出编号的待确认清单，用户按编号逐条回复，效率最高。

### 1.5 边界口径微调

```
己方的地雷不用管
```

### 1.6 棋盘形态修订（交点棋盘）

```
牌是放在线和线的交汇点上的
```

**效果**：棋盘从"格子盘"改为"线条盘"（横竖各 5 条线、25 个交点），文档全篇"格"改"交点"，引擎不受影响。

### 1.7 布局硬约束

```
牌和牌之间保持空间，不要有倾轧覆盖
```

**效果**：落档为硬性约束（卡宽=交点间距 70%~80%，热区不缩水，动画层例外）。

## 六、可复用的提示词模式总结

| 模式 | 提示词骨架 | 适用场景 |
|---|---|---|
| **从实物/想法启动** | "这是 XX，我想做成 XX，卡片/外观保持一致，规则与 XX 一致，**先完善需求文档**" | 任何复刻类项目第一步，先文档后代码 |
| **批量拍板** | 让 AI 先产出"编号待确认清单"，然后逐号回复 | 需求收敛期，减少来回 |
| **规则微调** | 一句话新规则 + （可选）边界问题 | 依赖 AI 已建立的文档上下文 |
| **进度看板** | "生成项目进度总结文档，并**根据开发进度实时更新**" | 跨会话协作的基础设施，尽早建立 |
| **缺陷反馈** | 截图 / 报错原文 + 一句话现象 | 越原始的报错信息定位越快，不要转述 |
| **样式反馈** | 截图 + 圈注 + 一句话说期望效果 | UI 调整 |
| **合规咨询** | "类目选什么" / "如何填写这个" | 发布前把 AI 当顾问，产出要落档备查 |

**跨阶段经验**：
1. **文档驱动**：需求文档 + 进度文档两份基线贯穿全程，每次改动先落档再动码；
2. **截图反馈闭环**：模拟器/真机截图 → AI 定位 → 修复 → 自检（60 局 AI 对局 + 引擎 35 测试）→ 重新编译验证；
3. **账号类型陷阱**：微信"小程序"与"小游戏"是两种账号，注册时类目决定一切，**不可互转**——新项目起步就要想清楚走哪条线。
